# 연관 데이터 조회 측정과 스터디 목록 페이지네이션 적용

## 문제 상황

* 스터디·댓글·신청 목록에서 작성자 닉네임이나 스터디 정보를 표시할 때 연관 엔티티 조회가 추가로 발생하는지 확인할 필요가 있었음
* 중복 신청 여부를 판단하기 위해 과거 신청 이력 전체를 엔티티로 읽는 방식도 점검할 필요가 있었음
* 스터디 목록을 전체 조회하고 있어 데이터가 늘어날수록 한 번에 읽는 데이터와 화면에 표시하는 항목이 증가하는 구조였음
* 조회 방식을 변경한 뒤 실제로 무엇이 개선되었는지 설명하기 위해 동일한 기준의 측정 근거가 필요했음

## 원인

* 지연 로딩된 연관 엔티티는 화면에서 필드에 접근하는 시점에 추가 SQL을 실행할 수 있음
* 같은 영속성 컨텍스트에 이미 로딩된 데이터가 있으면 추가 조회가 가려질 수 있어 단순한 화면 확인만으로는 SQL 수를 정확하게 판단하기 어려움
* 중복 신청 검사는 존재 여부만 필요하므로 과거 신청 전체를 로딩할 필요가 없음
* 목록 조회에 페이지 범위와 명시적인 정렬 기준이 없었음

## 해결 방법

* 스터디·댓글·신청 조회에서 화면에 필요한 작성자, 신청자와 스터디 정보를 fetch join으로 함께 가져오도록 구성함
* 중복 신청 검사는 `PENDING`, `APPROVED` 상태를 조건으로 하는 존재 여부 조회를 사용하도록 변경함
* `MySqlQueryOptimizationTest`에서 Hibernate Statistics로 SQL 수와 엔티티 로딩 수를 측정하도록 구현함
* 측정 전에 `flush()`, `clear()`, Statistics 초기화를 수행해 준비 데이터의 변경 SQL과 1차 캐시 영향을 측정에서 분리함
* 서로 다른 작성자의 데이터를 준비하고 Service 조회뿐 아니라 화면에서 사용하는 연관 필드 접근까지 측정에 포함함
* Flyway V2에 스터디·상태, 회원·스터디·상태 조건의 복합 인덱스를 추가하고 EXPLAIN으로 후보 인덱스와 실제 선택 결과를 확인함
* 확보한 `day9-before.log`와 `day9-after.log`의 SQL 수·엔티티 로딩 수·실행 계획이 같았다는 결과를 기록함
* 두 로그 모두 추가한 인덱스를 후보로 포함하고 있어 해당 기록만으로 인덱스 추가 전후의 성능 개선율을 계산하지 않도록 정리함
* 스터디 목록에 기본 10개·최대 50개의 페이지네이션과 `createdAt DESC, id DESC` 정렬을 적용함
* 현재 페이지 조회 테스트에서는 활성 스터디 25개를 준비하고, 요청한 페이지 크기만큼의 스터디와 작성자만 로딩하는지 검사하도록 구성함
* 페이지네이션 이전의 전체 목록 조회 기록과 이후의 페이지 데이터·전체 개수 조회를 서로 다른 측정 조건으로 구분함

## 배운 점

* 조회 코드를 변경했다는 사실만으로 성능이 개선되었다고 판단할 수 없으며, 실제 측정 결과와 조건을 함께 설명해야 한다는 것을 배웠습니다.
* JPA 조회를 확인할 때는 Service 호출뿐 아니라 화면에서 사용하는 연관 필드 접근까지 포함해야 추가 조회를 발견할 수 있다는 것을 알게 되었습니다.
* SQL 수, 엔티티 로딩 수와 응답 시간은 서로 다른 지표이므로 하나의 결과로 다른 지표의 개선을 주장해서는 안 된다는 것을 배웠습니다.
* 인덱스가 존재하더라도 실행 계획에서 항상 선택되는 것은 아니며, EXPLAIN의 예상 검사 행 수를 실제 처리 시간으로 해석해서는 안 된다는 것을 알게 되었습니다.
* 페이지네이션에서는 SQL 수뿐 아니라 한 번에 로딩하는 데이터 범위와 정렬의 일관성도 함께 확인해야 한다는 것을 배웠습니다.

# 스터디 신청 취소 후 재신청 불가 및 화면 상태 오류 버그 해결

## 문제 상황
- 사용자가 스터디 신청을 취소(`CANCELED`)한 후, 다시 해당 스터디 상세 페이지에 들어가면 여전히 "이미 신청한 스터디입니다"라고 뜨며 [신청하기] 버튼이 비활성화되는 문제 발생
- 또한, 강제로 재신청 API를 호출할 경우 DB 에러(중복 키 제약조건 위배)가 발생하며 서버 예외가 터지는 현상 확인

## 원인
- **DB 계층 (물리적 제약):** `Application` 엔티티에 `@UniqueConstraint(columnNames = {"member_id", "study_id"})`가 걸려있어, 상태(승인/취소/거절)와 무관하게 동일 회원이 동일 스터디에 두 번 이상 Row를 생성하는 것 자체가 DB 단에서 차단됨
- **Service 계층 (논리적 오류):** `isApplied` 메서드가 단순히 회원의 신청 내역 데이터가 '존재하는지'만 검사하고 있어, 과거에 취소했거나 거절당한 내역이 있어도 `true`를 반환해버림

## 해결 방법
- **엔티티 제약조건 해제:** 취소/거절 내역도 이력(History)으로 남기면서 재신청을 허용하기 위해, 엔티티 클래스의 `@UniqueConstraint`를 제거함
- **비즈니스 로직(검증) 이관:** 무결성 검증의 책임을 DB 제약조건에서 서비스 레이어로 이관함. `isApplied` 로직을 리팩토링하여 상태가 대기 중(`PENDING`)이거나 승인(`APPROVED`)된 '유효한 신청 건'이 있을 때만 중복 신청으로 간주하도록(`true` 반환) 수정함

## 배운 점
- 상태 값(Status)을 가지는 데이터는 DB 단의 복합 유니크 키(Composite Unique Key)로 제약을 걸면 비즈니스 유연성(재신청 등)이 크게 떨어진다는 것을 배움
- 데이터의 무결성을 유지하는 방법에는 DB 제약조건(Hard)과 애플리케이션 레벨의 검증(Soft)이 있으며, 요구사항에 맞춰 적절한 계층에 검증 로직을 배치해야 함을 깨달음

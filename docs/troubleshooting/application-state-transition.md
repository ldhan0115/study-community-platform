# 참가 신청 상태 재변경 문제 해결

## 문제 상황

* 참가 신청이 승인된 후 다시 거절되거나 취소되는 등 이미 처리된 신청의 상태를 계속 변경할 수 있었음
* `APPROVED`, `REJECTED`, `CANCELED` 같은 최종 상태 사이에서도 제한 없이 상태 변경이 가능했음
* 이미 승인된 신청의 상태가 변경되면 승인 인원 계산과 모집 상태가 실제 신청 이력과 일치하지 않을 수 있었음

## 원인

* `Application`의 `approve()`, `reject()`, `cancel()` 메서드가 현재 상태를 확인하지 않고 새로운 상태를 바로 대입하고 있었음
* 상태를 나타내는 `ApplicationStatus`는 존재했지만 어떤 상태에서 어떤 상태로 변경할 수 있는지에 대한 전이 규칙이 구현되어 있지 않았음
* Service 호출 순서에 따라 신청 상태가 계속 덮어써질 수 있었음

## 해결 방법

* 새로 생성된 신청은 항상 `PENDING` 상태로 시작하도록 유지함
* `PENDING` 상태에서만 `APPROVED`, `REJECTED`, `CANCELED` 중 하나로 변경할 수 있도록 규칙을 정의함
* 상태 변경 로직을 `changeStatus()`로 모으고 `validatePendingStatus()`를 통해 현재 상태를 먼저 검증하도록 변경함
* 이미 최종 상태가 된 신청을 다시 변경하려 하면 `IllegalStateException`이 발생하도록 처리함
* 승인 처리에서는 정원 계산 전에 신청 상태를 검증하여 이미 처리된 신청이 승인 인원 계산에 영향을 주지 않도록 함
* 파라미터화 테스트를 이용해 3개의 정상 전이와 최종 상태 사이의 9개 잘못된 전이를 검증함
* 잘못된 상태 변경 요청이 실패한 후에도 기존 상태가 그대로 유지되는 것을 확인함

## 배운 점

* 상태를 나타내는 Enum을 만드는 것만으로는 비즈니스 규칙이 보장되지 않으며 허용되는 상태 전이를 코드로 명시해야 한다는 것을 배웠습니다.
* 상태 변경 규칙을 Controller나 Service에 분산시키기보다 상태를 소유한 도메인 엔티티 내부에 두는 것이 일관성을 지키는 데 유리하다는 것을 알게 되었습니다.
* 여러 입력 조합을 검증해야 하는 상태 전이 테스트에서는 파라미터화 테스트를 활용하면 중복 코드를 줄이면서 모든 경우를 명확하게 검증할 수 있다는 것을 배웠습니다.

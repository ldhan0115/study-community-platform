# 동시 신청·승인에서 중복 신청과 정원 초과 방지

## 문제 상황

* 순차 요청에서는 중복 신청과 정원 초과를 검사하고 있었지만, 여러 요청이 동시에 실행될 때도 같은 규칙이 유지되는지 확인할 필요가 있었음
* 정원이 한 자리 남은 상황에서 두 승인 요청이 같은 승인 인원을 읽으면 모두 정원 검사에 통과할 수 있는 구조였음
* 동일 회원의 두 신청 요청이 동시에 유효한 신청이 없다고 판단하면 중복 신청이 생성될 가능성이 있었음
* 같은 신청에 대한 승인·취소 또는 승인·거절, 승인과 정원 축소가 동시에 발생하는 경우도 함께 고려해야 했음

## 원인

* `@Transactional`로 검사와 변경을 묶는 것만으로는 다른 트랜잭션과의 실행 순서가 정해지지 않음
* 중복 여부나 승인 인원을 조회한 시점과 실제 데이터를 변경하는 시점 사이에 다른 요청이 개입할 수 있었음
* 서로 다른 `Application`을 변경하는 요청도 같은 스터디의 모집 정원에 영향을 주므로, 개별 신청만 보호해서는 전체 정원 규칙을 지키기 어려웠음

## 해결 방법

* `StudyRepository.findActiveByIdForUpdate()`에 `PESSIMISTIC_WRITE` 잠금을 적용함
* 같은 스터디의 신청·승인·거절·취소·정원 변경·삭제가 공통으로 Study 행 잠금을 사용하도록 변경함
* 변경 Service에 `READ_COMMITTED`를 적용하고 잠금을 획득한 뒤 중복 신청 여부, 현재 신청 상태와 승인 인원을 검사하도록 처리함
* 기존 신청 변경 시에는 부모 스터디 ID만 먼저 조회하고, Study 잠금을 획득한 다음 실제 `Application`을 조회하도록 순서를 정리함
* 취소·거절 이력을 보존하면서 재신청할 수 있도록 단순한 회원·스터디 UNIQUE 제약 대신 잠금 안에서 유효 상태인 `PENDING`, `APPROVED`의 존재 여부를 확인함
* `MySqlConcurrencyTest`에서 별도 스레드로 실제 Service 프록시를 호출하고 각 요청의 커밋 또는 실패 결과를 확인하도록 구성함
* 작업이 모두 종료된 뒤 JDBC로 DB를 다시 조회하여 승인 수, 유효 신청 수와 최종 상태를 검사하도록 구현함
* 잠금을 의도적으로 보유한 상태에서 변경 요청을 실행해 잠금 실패와 기존 데이터 유지 여부를 검사하는 테스트를 추가함
* `PessimisticLockingFailureException`은 전역 예외 처리에서 HTTP 409와 재시도 안내를 반환하도록 처리함

## 배운 점

* 트랜잭션을 적용하는 것과 동시 요청 사이에서 비즈니스 규칙을 지키는 것은 별도로 검토해야 한다는 것을 배웠습니다.
* 잠금 대상은 수정하는 엔티티만 보고 결정하기보다 여러 요청이 함께 지켜야 하는 규칙의 범위를 기준으로 선택해야 한다는 것을 알게 되었습니다.
* 승인 요청만 보호하면 정원 변경이나 신청 취소 같은 다른 경로가 남을 수 있으므로 관련 변경 작업에 일관된 잠금 규칙을 적용해야 한다는 것을 배웠습니다.
* 동시성 테스트에서는 최종 DB 상태뿐 아니라 각 요청이 실제로 성공했는지, 어떤 이유로 실패했는지도 확인해야 한다는 것을 배웠습니다.
* 비관적 잠금은 정합성을 보호하지만 같은 스터디의 요청에 대기 시간이 생길 수 있으므로, 실제 부하에서의 처리량과 지연은 추가 측정이 필요하다는 것을 알게 되었습니다.

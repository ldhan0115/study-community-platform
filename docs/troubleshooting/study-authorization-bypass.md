# 스터디 수정·삭제 권한 검증을 Service 계층으로 이동

## 문제 상황

* 스터디 수정·삭제 권한을 Controller에서만 검증하고 있었음
* `StudyService.updateStudy()`와 `deleteStudy()`는 로그인 회원 정보 없이 스터디 ID만 전달받고 있어 Service 자체적으로 작성자 권한을 검증할 수 없었음
* 다른 Controller나 새로운 호출 경로에서 Service를 사용할 경우 권한 검증이 누락될 가능성이 있었음

## 원인

* 화면 요청을 처리하는 Controller가 권한 검증과 비즈니스 로직 호출을 모두 담당하고 있었음
* Service는 호출한 사용자가 정상적인 권한을 가지고 있을 것이라고 가정하고 있었음
* 핵심 비즈니스 규칙인 “스터디 작성자만 수정하거나 삭제할 수 있다”는 조건이 특정 웹 요청 흐름에만 의존하고 있었음

## 해결 방법

* `updateStudy()`와 `deleteStudy()`가 로그인 회원 ID를 함께 전달받도록 메서드 구조를 변경함
* `StudyService` 내부에 `validateStudyOwner()`를 추가하여 로그인 회원과 스터디 작성자를 비교하도록 함
* 스터디 수정 화면에 진입할 때도 `findStudyForOwner()`를 통해 조회와 작성자 권한 검증을 함께 수행하도록 변경함
* 실제 엔티티를 변경하거나 논리적으로 삭제하기 전에 Service에서 권한을 먼저 검증하도록 처리함
* 다른 회원이 수정·삭제를 요청하면 예외가 발생하고 기존 스터디 정보가 변경되지 않는 것을 테스트로 검증함

## 배운 점

* 권한 검증은 특정 Controller에만 두는 것이 아니라 비즈니스 로직이 실행되는 Service 계층에서도 보장해야 한다는 것을 배웠습니다.
* Service가 현재 요청한 사용자 정보를 전달받아야 리소스 소유자와 비교하고 비즈니스 규칙을 독립적으로 지킬 수 있다는 것을 알게 되었습니다.
* 권한 검증을 데이터 변경보다 먼저 수행해야 권한 없는 요청이 엔티티 상태에 영향을 주는 것을 방지할 수 있다는 것을 배웠습니다.

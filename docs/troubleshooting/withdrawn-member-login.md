# 탈퇴 회원 재로그인 문제 해결

## 문제 상황

* 회원 탈퇴 시 데이터를 실제로 삭제하지 않고 `deletedAt`에 탈퇴 시간을 기록하는 논리적 삭제 방식을 사용하고 있었음
* 탈퇴 직후 기존 세션은 무효화되지만 같은 로그인 ID와 비밀번호를 입력하면 다시 로그인할 수 있었음
* 서비스에서 탈퇴한 회원을 일반 회원과 동일하게 조회할 수 있는 문제도 존재했음

## 원인

* 로그인 시 `findByLoginId()`를 사용하여 `deletedAt` 상태와 관계없이 회원을 조회하고 있었음
* 탈퇴 회원의 비밀번호 해시도 DB에 보존되기 때문에 비밀번호가 일치하면 기존 로그인 로직을 그대로 통과했음
* 논리적 삭제를 적용하면서 데이터를 삭제하는 처리만 구현하고 이후의 조회 조건을 함께 변경하지 않았음

## 해결 방법

* `MemberRepository`에 `findByLoginIdAndDeletedAtIsNull()`을 추가하여 활성 회원만 로그인 대상으로 조회하도록 변경함
* 회원 ID 조회에도 `findByIdAndDeletedAtIsNull()`을 적용하여 탈퇴 회원이 일반적인 회원 기능에 다시 접근하지 못하도록 함
* `MemberService.login()`에서 활성 회원 조회 결과에 대해서만 `PasswordEncoder.matches()`를 실행하도록 변경함
* 회원 수정과 탈퇴 처리에서도 활성 회원 조회 메서드를 사용하여 이미 탈퇴한 회원을 다시 처리하지 않도록 함
* 탈퇴 회원의 로그인 ID, 이메일, 닉네임은 재사용하지 않는 정책에 따라 기존 중복 검사에서는 탈퇴 회원 데이터도 계속 포함하도록 유지함
* 테스트를 통해 정상 회원은 로그인할 수 있고 탈퇴 회원은 올바른 비밀번호를 입력해도 로그인할 수 없는 것을 검증함

## 배운 점

* 논리적 삭제는 `deletedAt` 값을 기록하는 것만으로 완성되는 것이 아니라 이후의 모든 조회와 인증 흐름에서 활성 데이터 조건을 일관되게 적용해야 한다는 것을 배웠습니다.
* 로그인처럼 보안과 직접 연결되는 조회에서는 삭제 여부를 애플리케이션에서 나중에 검사하기보다 Repository 조회 조건에 포함하는 것이 안전하다는 것을 알게 되었습니다.
* 논리적 삭제 데이터를 보존할 때는 로그인 차단, 정보 조회, 식별자 재사용 여부와 같은 운영 정책도 함께 결정해야 한다는 것을 배웠습니다.

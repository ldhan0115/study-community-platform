# 회원 정보 수정 후 로그인 세션 ID 유실 문제 해결

## 문제 상황

* 회원 정보를 수정한 후 로그인 세션에 저장된 회원 ID가 `null`이 되는 문제가 발생함
* 회원 ID가 필요한 스터디 등록, 신청, 댓글 작성 등의 기능에서 정상적인 로그인 회원을 식별할 수 없었음
* 회원 수정 화면에서 입력한 평문 비밀번호가 세션 객체에 포함되는 보안 문제도 함께 확인됨

## 원인

* 회원 수정 요청을 처리할 때 `Member.createMember()`로 새로운 `Member` 객체를 생성함
* 새로 생성한 객체는 JPA에 저장된 영속 엔티티가 아니므로 DB에서 발급한 회원 ID가 존재하지 않았음
* 서비스에서는 기존 영속 회원을 수정했지만, Controller에서는 새로 생성한 비영속 `Member` 객체를 세션에 저장하고 있었음
* 세션에 `Member` 엔티티 전체를 저장하면서 비밀번호와 같은 불필요한 정보까지 포함되고 있었음

## 해결 방법

* 로그인 세션 전용 DTO인 `LoginMemberSession`을 생성하고 회원 ID와 닉네임만 저장하도록 변경함
* 회원 수정 요청 데이터는 `MemberUpdateDto`로 분리하여 Service 계층에 전달함
* `MemberService.editMember()`에서 DB에 저장된 기존 회원을 조회한 후 영속 엔티티의 값을 변경하도록 수정함
* 회원 수정 후에는 Service에서 반환한 영속 회원을 기준으로 `LoginMemberSession`을 다시 생성하여 세션을 갱신함
* 회원 수정 화면에 필요한 로그인 ID, 이메일, 닉네임은 세션이 아닌 DB에서 최신 회원 정보를 조회하여 사용함
* 테스트를 통해 회원 수정 후에도 기존 회원 ID가 유지되고 세션 객체에 비밀번호가 포함되지 않는 것을 검증함

## 배운 점

* JPA 엔티티의 ID는 DB에 저장된 영속 엔티티에 부여되므로 새로 생성한 비영속 객체에는 기존 회원 ID가 유지되지 않는다는 것을 배웠습니다.
* 세션에는 엔티티 전체를 저장하기보다 인증과 화면 표시에 필요한 최소한의 정보만 저장해야 한다는 것을 알게 되었습니다.
* 요청 DTO, 세션 DTO, 영속 엔티티의 역할을 분리하면 계층 간 책임이 명확해지고 민감한 정보가 불필요하게 노출되는 문제도 방지할 수 있다는 것을 배웠습니다.

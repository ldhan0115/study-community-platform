# 스터디 참가 신청 권한 우회 문제 해결

## 문제 상황

* 스터디 방장에게만 신청 승인·거절 버튼을 표시하고 있었지만, 직접 HTTP 요청을 보내는 경우에도 서버에서 권한을 보장할 필요가 있었음
* 기존 승인·거절 요청에서는 `applicationId`와 `studyId`를 클라이언트로부터 각각 전달받고 있었음
* 자신이 작성한 스터디의 `studyId`와 다른 스터디의 `applicationId`를 조합하면, 권한을 확인한 스터디와 실제 변경 대상 신청이 달라질 수 있었음
* 신청 취소 권한도 Controller에서만 검사하면 Service를 직접 호출하는 다른 경로에서 검증이 누락될 수 있었음

## 원인

* 클라이언트가 전달한 `studyId`를 실제 신청 대상 스터디라고 신뢰하고 권한 판단에 사용함
* 권한 검증에 사용한 스터디와 상태를 변경할 `Application`의 실제 연관관계를 함께 확인하지 않았음
* 승인·거절·취소에 필요한 권한 규칙이 데이터 변경을 담당하는 Service 계층에서 일관되게 적용되지 않았음

## 해결 방법

* Controller에서 인증 정보로 확인한 회원 ID와 `applicationId`를 Service에 전달하도록 변경함
* 승인·거절 권한은 클라이언트가 전달한 `studyId`가 아니라 `Application → Study → Member`의 실제 연관관계를 기준으로 판단하도록 변경함
* `ApplicationService.validateStudyOwner()`에서 요청 회원과 실제 스터디 작성자를 비교하도록 구현함
* `ApplicationService.validateApplicant()`에서 요청 회원과 실제 신청자를 비교하도록 구현함
* 권한 검증을 통과한 뒤 신청 상태와 모집 정원 규칙을 검사하고 데이터를 변경하도록 처리함
* 승인·거절 Service가 실제 스터디 ID를 반환하도록 하여 Controller에서 리다이렉트를 위한 신청 선조회를 제거함
* `ApplicationServiceTest`에 타인의 승인·거절·취소 요청에서 예외가 발생하고 기존 신청 상태가 유지되는지 검사하는 테스트를 작성함
* `SecurityHttpFlowTest`에서는 실제 로그인 세션과 유효한 CSRF 토큰을 사용해 HTTP 403 응답과 요청 전후 DB 데이터 유지 여부를 검사하도록 구성함

## 배운 점

* 화면에서 버튼을 숨기는 처리는 서버의 권한 검증을 대신할 수 없다는 것을 배웠습니다.
* 요청으로 전달받은 여러 ID가 서로 올바른 관계라는 가정을 해서는 안 되며, 서버에서 조회한 실제 연관관계를 기준으로 권한을 판단해야 한다는 것을 알게 되었습니다.
* 데이터 변경을 담당하는 Service 계층에서 권한을 검사하면 호출 경로가 달라져도 같은 규칙을 적용할 수 있다는 것을 배웠습니다.
* 권한 없는 요청에서 예외가 발생하는 것뿐 아니라 기존 데이터가 변경되지 않았는지도 함께 확인해야 한다는 것을 배웠습니다.

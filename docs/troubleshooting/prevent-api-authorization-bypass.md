# 스터디 참가 신청 권한 우회 문제 해결

## 문제 상황

* 스터디 방장에게만 신청 승인·거절 버튼을 보여주고 Controller에서 권한을 검증하고 있었음
* 승인·거절 요청에서 `applicationId`와 `studyId`를 클라이언트로부터 각각 전달받고 있었음
* 사용자가 자신이 작성한 스터디의 `studyId`와 다른 스터디의 `applicationId`를 조합해 요청하면 권한 검증을 통과할 가능성이 있었음
* 신청 취소 권한도 Controller에서만 확인하고 있어 Service를 직접 호출하는 다른 경로에서는 검증이 보장되지 않았음

## 원인

* 클라이언트가 전달한 `studyId`를 실제 신청 대상 스터디라고 신뢰하고 권한 검증에 사용함
* 권한 검증에 사용한 스터디와 상태를 변경할 `Application` 사이의 실제 연관관계를 확인하지 않았음
* 신청 승인·거절·취소에 필요한 권한 검증이 Service 계층에 포함되어 있지 않았음

## 해결 방법

* 승인·거절 요청에서 클라이언트가 전달하는 `studyId`를 권한 판단 기준으로 사용하지 않도록 변경함
* Service에서 `applicationId`로 `Application`을 조회한 후 `Application → Study → Member` 연관관계를 따라 실제 스터디 작성자를 확인하도록 수정함
* `validateStudyOwner()`를 추가하여 실제 스터디 작성자만 신청을 승인하거나 거절할 수 있도록 함
* `validateApplicant()`를 추가하여 실제 신청자 본인만 신청을 취소할 수 있도록 함
* 승인·거절·취소 메서드가 로그인 회원 ID와 신청 ID를 함께 전달받도록 변경함
* 다른 스터디 방장이나 제삼자의 요청은 예외가 발생하고 신청 상태가 `PENDING`으로 유지되는 것을 테스트로 검증함

## 배운 점

* 화면에서 버튼을 숨기는 것은 사용자 경험을 위한 처리일 뿐 서버의 권한 검증을 대신할 수 없다는 것을 배웠습니다.
* 클라이언트가 전달하는 ID와 리소스 간 관계는 조작될 수 있으므로 권한 판단에 그대로 신뢰해서는 안 된다는 것을 알게 되었습니다.
* 권한 검증에는 요청 파라미터가 아니라 서버에서 조회한 엔티티의 실제 연관관계를 사용해야 안전하다는 것을 배웠습니다.
